# 邮箱验证码变更重试设计

**日期**：2026-07-19
**状态**：已确认，待实现

## 目标

当 OpenAI 邮箱验证码提交失败时，继续监听同一个邮箱；只有发现新的不同验证码才再次提交，最多提交两个不同验证码。

## 当前问题

- `core.email_provider.wait_for_otp()` 能按 `after_ts` 等待新验证码，但调用方拿到验证码后只提交一次。
- 初始注册和 2FA 重认证分别调用验证码提交逻辑，失败行为不统一。
- 相同验证码不能重复提交，否则会重复消耗无效尝试并掩盖邮箱接口没有更新的问题。

## 方案

增加共享的验证码提交重试器，由调用方传入“获取验证码”和“提交验证码”函数：

1. 发送验证码后固定 `after_ts`，整个阶段不重置时间基准。
2. 获取第一个新验证码并提交。
3. 提交失败后继续轮询邮箱接口。
4. 返回值与已经提交过的验证码相同时，只等待，不重复 POST。
5. 返回第二个不同验证码后再次提交。
6. 两个不同验证码都失败，返回最后一次错误。

现有轮询配置继续生效：默认最长 120 秒、每 3 秒检查一次。重试期间复用同一个 Roxy CDP 会话、指纹、出口 IP 和授权上下文，不刷新 profile。

## 适用范围

- 初始注册邮箱验证码。
- 注册完成后的 2FA 重认证邮箱验证码。

不修改：验证码接口本身、Roxy 指纹/IP 刷新策略、数据库成功写回条件。

## 错误边界

- 相同验证码：继续监听，不重复提交。
- 新验证码提交失败：最多再等待并提交一个不同验证码。
- 401/409 等授权状态错误：仍按已确认规则最多尝试第二个新验证码；若仍失败，保留完整错误阶段信息，不刷新环境。
- 未拿到 TOTP secret：不写入 `codex_2fa`，不将协议注册标记为成功。

## 日志与安全

- 记录验证码阶段、尝试序号和等待原因。
- 不输出验证码明文、密码、access token 或 TOTP secret。
- 成功写回仍由父服务验证结构化 `registrationMfa.secret` 后执行。

## 验证

- 单元测试：相同验证码不会重复提交；新验证码最多提交两次；第二次成功后停止轮询；两个不同验证码均失败后返回错误。
- 集成回归：初始注册和 2FA 重认证都调用共享重试器。
- 运行 Python 协议测试、相关 Node 服务测试和 `git diff --check`。

## 备选方案

- 只修改 2FA 调用方：改动小，但初始注册仍可能丢失新验证码，不采用。
- 每次失败重新发送验证码：会增加授权状态变化和网络依赖，不符合复用同一 Roxy 会话的约束，不采用。
